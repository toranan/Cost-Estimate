# ORCA Engineering Case Study

이 문서는 채용 담당자와 협업자가 ORCA의 문제 정의, 설계 결정, 실패 경험, 현재 한계를 빠르게 이해할 수 있도록 정리한 기술 케이스 스터디입니다.

## 1. 해결하려는 문제

법안 비용추계는 문서를 요약하는 문제가 아닙니다. 조문에서 재정수반요인을 찾고, 대상·단가·횟수·시행 시점 같은 전제값을 결정한 뒤, 공식 기준에 맞는 5개년 산식을 작성해야 합니다.

LLM에 전 과정을 한 번에 맡겼을 때 다음 문제가 반복됐습니다.

- 근거 문서에 없는 인원과 단가를 자연스럽게 만들어냄
- 같은 입력에서도 산식과 연도별 금액이 달라짐
- 비용추계가 불가능한 법안에도 임의 값을 채움
- 사용자가 어떤 가정을 수정해야 하는지 알기 어려움

제품 목표를 “완성된 정답 자동 생성”이 아니라 **근거를 확인하고 수정할 수 있는 비용추계 초안 생성**으로 정의했습니다.

## 2. 프로젝트 맥락과 담당 영역

프로젝트는 동국대학교 컴퓨터공학과 캡스톤·산학협력 과제로 시작했습니다. 현재 포트폴리오 저장소에서 집중한 영역은 다음과 같습니다.

- 국회 문서 수집, 청킹, 임베딩, TAG 구조화 데이터 파이프라인 연결
- PDF 개정분 추출부터 조문 분석, 판정, 계산, 출력까지 end-to-end 통합
- 양식별 정책 게이트와 Python 연도별 계산 엔진
- React 결과 대시보드, 근거 표시, 사용자 전제값 재계산, PDF 출력
- 실제 공식 문서와의 비교를 통한 오류 원인 분석과 회귀 기록

생성형 AI는 코드 초안, 탐색, 디버깅 가설 수립에 적극 활용했습니다. 최종 판단은 중간 JSON, 검색 결과, 실제 공식 문서, 단위 테스트를 대조하는 방식으로 검증했습니다. 현재 이해하거나 검증하지 못한 영역은 완료 성과로 표시하지 않습니다.

## 3. 시스템 경계

```text
문서 이해      LLM + 규칙
관련 근거 검색  pgvector RAG + 구조화 TAG
정책 판정      Python 금액 게이트 + 도메인 정책
금액 계산      Python 결정적 계산
사용자 검토    React UI + 근거 trace + recompute API
문서 출력      HTML/PDF/HWPX/DOCX renderer
```

이 경계의 핵심은 **계산이 재현 가능하다는 것과 전체 추계가 정확하다는 것을 구분**하는 데 있습니다. Python 계산이 정확해도 잘못된 대상 수와 단가를 넣으면 결과는 틀립니다.

## 4. 주요 오류와 설계 변화

### Cycle 1: 미첨부 판단 채널 부재

중대범죄수사청 설치법에 27억 원을 산출했지만 공식 판단은 조직 규모와 정원이 시행령에 위임되어 추계가 곤란하다는 것이었습니다.

원인은 데이터 부족이 아니었습니다. 미첨부 사유서 데이터를 수집해 놓고도 비용추계서 검색 채널만 분석 파이프라인에 연결한 구조적 비대칭이었습니다.

### Cycle 2: 단일 규칙의 오버피팅

조직 신설과 시행령 위임을 탐지하는 규칙을 추가하자 첫 사례는 해결됐지만, 구조가 비슷한 공소청 설치법에서 다시 잘못된 금액을 산출했습니다.

케이스별 규칙을 계속 추가하는 대신 비용추계서와 미첨부 사유서를 동시에 검색하고 채널별 유사도를 비교하는 Dual-Channel 구조로 전환했습니다.

### Cycle 3: 다수결의 함정

대구경북특별시 특별법은 추계 곤란 조문이 더 많았지만, 공식 문서는 산출 가능한 일부 조문만으로 비용추계서를 작성했습니다. 조문 다수결 방식은 이를 미첨부로 오판했습니다.

이를 통해 “산출 가능한 조문이 하나라도 있으면 그 부분을 추계한다”는 존재 게이트를 도입했습니다.

### Cycle 4: 합계 행 이중계산

TAG 선례에서 개별 항목과 합계 행을 함께 가져와 금액이 정확히 두 배가 되는 버그가 발생했습니다. 구조화 문서의 `합계·총계·소계` 행을 계산 항목에서 제외하고 반대 방향 사례를 함께 회귀 점검했습니다.

상세 입력과 결과는 [IMPROVEMENTS.md](./IMPROVEMENTS.md)에 기록했습니다.

## 5. 데이터 부족과 검색 실패를 구분하기

최근 조세지출 일몰 연장 사례에서는 두 문제가 함께 존재했습니다.

1. 같은 조문 선례에 방법론과 과거 기준값이 있었지만 전체 의안 임베딩 검색이 이를 찾지 못함
2. 최신 실적값은 부처 제출자료에만 있어 외부 공개 데이터만으로 정확히 재현하기 어려움

첫 번째는 **검색 구조 문제**, 두 번째는 **실제 데이터 경계**입니다. 둘을 모두 “데이터가 없다”로 처리하면 검색기를 개선할 기회를 놓칩니다.

현재 코드에는 감면·면제·적용기한 연장을 재정수입 감소 후보로 유지하는 1차 정책 보정이 작업 중입니다. 그러나 다음 항목은 아직 완료되지 않았습니다.

- 제안이유와 조문 제목에서 개정 대상의 실체 키워드 추출
- 실체 키워드 기반 비용추계 채널 보강 검색과 결과 병합
- 선례 근사값을 `similar_case`로 명시하고 최신 실적 부재를 별도 경고
- 조세지출 사례의 독립 회귀 테스트

따라서 이 사례는 현재 **원인 분석 완료, 판정 보정 일부 구현, 검색 개선 미완료** 상태입니다.

## 6. 검증을 어떻게 해석하는가

현재 8건 비교는 개발 과정의 회귀 스냅샷입니다.

- 비용추계서/미첨부 방향: 8건 일치
- 금액을 비교할 수 있는 사례: 4건
- 3건은 공식 금액 대비 1% 이내, 1건은 전제 차이로 21% 오차
- 계산·정책 관련 단위 테스트: 23개

이 수치는 일반화 성능을 증명하지 않습니다. 일부 공식 문서가 검색 풀에 포함될 수 있고, 오류 사례를 보며 임계값과 정책을 수정했기 때문입니다.

다음 평가에서는 다음을 분리해야 합니다.

| 평가 대상 | 지표 | 분리 기준 |
|---|---|---|
| 비용유발 조문 탐지 | precision, recall, F1 | 의안 단위 holdout |
| 비용추계/미첨부 판정 | macro F1, confusion matrix | 판정 유형 층화 표본 |
| 근거 검색 | recall@k, MRR | 동일 `bill_id` 정답 문서 제외 |
| 금액 | MAPE, 중앙값·최대 오차 | 산출 가능 사례만 별도 평가 |
| 사용자 효율 | 수정 횟수, 완료 시간 | 전문가 비교 실험 |

## 7. 현재 기술 부채

### API와 실행 모델

- PDF를 Base64 JSON으로 보내므로 파일 크기가 증가함
- 긴 분석을 동기 요청으로 처리해 timeout과 재시도 경험이 약함
- 인증, 권한, 고객 데이터 격리, rate limit이 없음

제품화한다면 객체 스토리지 직접 업로드, 비동기 작업 큐, idempotency key, 단계별 상태 API를 사용합니다.

### Frontend

- `App.jsx`가 업로드, 결과, 편집, 문서 미리보기를 함께 관리함
- API 응답 타입과 런타임 스키마 검증이 없음
- 실제 서버 진행 이벤트가 아닌 클라이언트 단계 표시를 사용함

기능별 컴포넌트와 custom hook으로 분리하고, TypeScript와 런타임 검증을 도입할 계획입니다.

### Evaluation

- 평가 세트가 작고 개발 세트와 엄격히 분리되지 않음
- 검색 임계값이 체계적인 precision-recall 실험보다 사례 기반 휴리스틱에 가까움
- 모델·프롬프트·데이터 버전별 결과 보존이 부족함

## 8. 3분 설명 구조

면접에서는 다음 순서로 설명할 수 있습니다.

1. 비용추계에서 가장 위험한 것은 자연스러운 문장이 아니라 근거 없는 전제와 숫자라고 정의했습니다.
2. LLM, 검색, 정책 판정, 계산의 책임을 분리하고 사용자가 근거와 전제값을 검토할 수 있게 만들었습니다.
3. 미첨부 채널 부재, 규칙 오버피팅, 다수결 오류, 이중계산을 실제 공식 문서 비교로 발견했습니다.
4. 오류 하나를 막는 규칙보다 양방향 검색과 존재 게이트 같은 구조적 개선을 선택했습니다.
5. 현재 결과는 작은 회귀 테스트이며, 엄격한 holdout과 프로덕션 보안·비동기 처리는 다음 과제라고 구분합니다.
