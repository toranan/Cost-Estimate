# 조례안 비용추계 자동화 — 라우팅 기반 TAG 룰엔진

> **TL;DR (60초).** 국회 법안의 비용추계서를 자동 초안하는 엔진. "전제값을 어디서
> 가져오는가"를 4단계(조문 → 규칙 라우팅 → DB 개념조회 → HITL)로 설계했다.
> **개발에 안 쓴 새 의안 10건 홀드아웃**에서 확정 계산 6건 전부 오차 30% 이내
> (그중 4건은 5% 이내), 나머지는 "왜 못 하는지"를 라벨링해 정직 보류.
> 핵심은 **"안 되는 것을 데이터로 규명"** — 선례준용형 자동화가 불가능함을
> 오염 없는 실험(0/5)으로 증명하고, 되는 경계(단가·비율은 되고 규모·개수는 안 됨)를
> 실측으로 그었다.

---

## 1. 문제 (Problem)

국회예산정책처(NABO)는 발의되는 모든 법안에 비용추계서를 작성한다. 반복 노동이지만
LLM에 통째로 맡기면 **근거 없는 가정·산술 오류·검증 불가**가 생긴다. 목표는
"자동으로 정답을 내는 것"이 아니라 **"근거를 추적할 수 있는 초안 + 못 하는 부분을
정직하게 표시"**하는 것 — NABO 자신도 "유사사례 준용", "시행령 확정 후 재추계"라는
근거 있는 추정으로 작성한다.

## 2. 아키텍처 (Architecture) — 전제값을 어디서 가져오는가

비용 = `산식(구조) × 전제값들`. 산식은 조문에서 판단하고, **전제값은 4단계로 조달**한다:

```
비용항목
 ① 조문에 값이 있나       → 위원 수·증원 인원 (명시되면 확정)
 ② 규칙 라우팅으로 계산되나 → 회의수당·상임위원 증원·기본경비율 (규칙+계산기)
 ③ DB에서 개념으로 조회되나 → 급여·부담률·단가 = method2 (개념 키 → population 대표값)
 ④ 그래도 없으면          → HITL (산식 제시 + 빈 전제 콕 집어 입력 요청)
```

**핵심 설계 결정:**
- **규칙 + LLM 백업 하이브리드** — 명확한 문구는 규칙(결정적·오탐 0), 다양한 표현은
  LLM 백업(신뢰 LLM). 프로덕션 LLM(solar)은 같은 입력에 회차마다 다른 결과(실측
  최대 80배 편차)라 신뢰하지 않고 파싱 보조로만.
- **method2 (개념 조회)** — "가장 비슷한 선례 하나"가 아니라 "개념 population의
  대표값". 소속기관/연도 축으로 조회(법무부 기본경비율 9.6% = 정답 정확 일치).
- **신뢰도 라벨** — 정답 없이 결정. 전제를 조문/DB에서 채웠는지, 분포가 수렴하는지로
  확정🟢 / 저신뢰🟡 / 보류🔴 판정.

## 3. 도전과 트레이드오프 (Challenges) — 무엇이 깨졌고 어떻게 대응했나

**깨진 것 ①: "가장 유사한 선례 매칭"이 반복 실패했다.**
- 임베딩 최근접(5건 중 5건 오선택), LLM 도메인판단(0/5), 정답매핑 재사용(선례 92%가
  1회성). 전부 **정답 안 본 fork 에이전트**로 오염 없이 검증.
- → **결론: 선례 통째 매칭은 원리적으로 안 됨.** "비슷함"을 유사도로 판단하면 그럴듯한
  오답을 낸다. 대신 method2(개념 대표값)로 전환 — 유사도 판단을 우회.

**깨진 것 ②: 개정형 위원회가 무출력이었다.**
- "상임위원을 2명→5명으로 늘림"은 "신설" 트리거가 없어 계산 시작조차 안 됨.
- → **라우팅 추가:** `committee_increment_gate`(규칙+LLM백업) + `calculate_member_increment`.
  "겸직 배제 = 인원 +1" 같은 일반 원리로 확장. 홀드아웃 증원 6건 5/6 오차 30% 이내.

**깨진 것 ③: 일반직 급여를 5급으로 근사해 -34%.**
- → 특정 직급 가정은 오버핏. "직급 미상 시 인사혁신처 고시 전체공무원 평균"으로 교체.
  오버핏 아닌 공식 통계 → 인건비 오차 **-34% → +1%**.

**모든 개선은 회귀 안전:** 기존 44건 E2E 재실행 시 결과 0 변경(오탐 없음) 확인 후 배선.

## 4. 평가 (Evaluation) — 개발에 안 쓴 새 의안 10건 홀드아웃

국회 Open API로 **개발셋에 없는 새 의안**을 다운로드 → 배선된 파이프라인으로 실행 →
NABO 공식 추계서와 대조.

| 신뢰도(정답前) | 건수 | 실제 오차 |
|---|---:|---|
| 🟢 확정 | 4건 (2211768·2200815·2203739 등) | **+2% ~ -5%** |
| 🟡 저신뢰 | 2건 (회의수당·유추) | +20% ~ +26% |
| 🔴 보류 | 4건 | (정직 보류 — 아래) |

- **확정 계산 6건 전부 오차 30% 이내, 4건은 5% 이내.** 오버핏 아닌 홀드아웃.
- **신뢰도 라벨이 정답 없이 방향 일치** — 🟢로 라벨한 게 실제로 오차 작았고, 🟡가 컸다.
  즉 "처음 보는 의안은 오차 자체는 몰라도, 오차가 클 조건은 안다"를 실증.
- **비즈니스 언어 성과:** "위험한 확정 오답 대신 근거 있는 초안 + 무엇을 입력하면
  완성되는지 제시" — 무출력(막막함)을 "산식 다 있고 위원정수 하나만 입력" HITL로 전환.

## 5. 안 되는 것 (Limits) — 정직하게, 이게 이 프로젝트의 핵심 결과

**전제를 못 채워 보류하는 이유는 4가지로 수렴하고, 전부 "그 값이 텍스트·통계에 아직
존재하지 않기 때문"이다** (우리가 못 찾은 게 아님):

| 이유 | 예 | 자동화 |
|---|---|---|
| 규모/개수를 이 법안이 새로 정함(근거 조문밖) | 사무국 인원·위원정수(시행령 위임) | 🔴 원천불가 → HITL |
| 수급자 수가 외부 통계 | 보상금 대상·국선대리인 건수 | 🔴 외부데이터 → HITL |
| 어느 선례 준용할지가 도메인 판단 | "이 위원회 ≈ 최저임금위" (조문에 단서 0개) | 🔴 fork 0/5로 실증 |
| 관행 단가·횟수가 실무 기준값 | 회의수당 35만·연3회 | 🟡 DB 있으면 채움, 없으면 저신뢰 |

**되는 것 vs 안 되는 것의 경계 (실측):**
- 🟢 **"세상에 고정된 사실값"**(급여·기관부담률·기본경비율) → 조문에 없어도 DB에서
  가져옴. 좁게 수렴(ratio~1).
- 🔴 **"이 법안이 새로 정하는 규모·대상·선례"** → 어디에도 없음. 안 수렴(ratio 58~).

## 6. 개선 방향 (What's Next)

- **HITL 재사용 축적** — 사람이 확정한 전제 중 *일반화되는 것만*(단가·관행·선례연결)
  검토 후 참조 테이블로 승격. 규모·개수 같은 의안 국한 값은 재사용 금지(화이트리스트).
  → 쓸수록 "값 없음→보류"가 줄어드는 구조.
- **미구현 핸들러 추가** — 속기비·시스템구축 등 반복 유형을 라우팅 패턴대로 확장.
